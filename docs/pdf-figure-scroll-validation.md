# 首次自动补图的滚动响应

2026-10-16；未提交测试构建，版本仍为 1.6.13。
当前运行文件指纹：`d201262618fb71f022a0ca6303a74e914061bfa3021dc3efdfe93fba30d2f953`。

## 现象与已确认范围

用户确认仅第一次经过需要补图的位置卡顿，返回同一幅图不反复卡顿。
只读核对确认其安装的 XPI 与上一轮 figure-cache-test 包哈希一致，设置为自动补图；
插件专属目录已有 18 个 PNG。没有修改用户配置、安装包、PDF 或现有缓存。

旧代码会在滚动和观察器回调后立即开始近视口的首次渲染；大图像素扫描与
`toDataURL` PNG 编码连续占用界面线程。`async` 函数中的同步循环仍在界面线程执行。

在旧 XPI 提取的同一份运行脚本上，以下命令已实际运行并触发两项失败：

```powershell
# ZRB_SCROLL_SOURCE 指向从旧 XPI 提取的 pdf-figure-fallback.js
node --test tests/browser/figure-scroll.test.cjs
```

1. 3000×3000 图的扫描/编码期间，输入计时任务运行 0 次，连续处理约 141 ms。
2. 标准模式 iframe 的真实连续滚轮输入中，原 PDF 渲染在输入间隔内提前启动。
   测试以实际送达的 wheel 事件计时，避免其他测试造成自动化调用延迟而误判。

真实 Gecko 系统/内容权限下，同一大图旧版处理约 125 ms，输入任务仍为 0 次。
这证明了两个可复现的卡顿触发；没有录制用户桌面的性能轨迹，不能据此排除其他原因。

## 修改

- 被动监听 wheel/scroll，只记录时间、合并检查。滚动停稳约 160 ms 后，
  才检查可见范围并启动新的自动原图渲染；在队列中等待的任务也重新检查。
- 像素扫描分段执行，每约 6 ms 让出执行机会；检测到滚动时暂停扫描直到停稳。
  像素一次读取，避免多次画布回读造成额外延迟。
- 改用异步 PNG 编码及读取。裁剪边界、分辨率和缓存键算法保持一致，
  不通过降低清晰度改善响应。计时器关闭时释放，关闭视图的迟到结果继续丢弃。
- 手动点击仍能直接发起；自动模式的图片可能稍晚出现，以优先保持滚动响应。

这并没有把所有 PDF 处理移入工作线程。Reader 原生区域渲染及其内部 PNG
序列化仍有同步阶段；首次补图的总耗时也不承诺缩短。

全套并发浏览器测试中，大图处理期间可穿插 14 次计时任务；真实滚轮后约 183 ms
才启动渲染。Gecko 权限用例中可穿插 12 次计时任务。任务能够穿插执行是本次
主要指标；不把不同测试负载下的总处理时间当作加速比例。

实际 PDF 的 16 ms 计时探针结果也保留局限：

| 文献 | 改前超过 50 ms 的间隔次数 | 改后次数 | 改前/改后最大间隔 |
| --- | --- | --- | --- |
| Carneiro/Gamboa | 10 | 5 | 82 / 82 ms |
| LRQ-Solver | 4 | 3 | 114 / 120 ms |

该探针没有模拟持续滚轮，包含原生 PDF 渲染等整个冷加载过程。次数减少，
最坏峰值未一致下降，因此不能声称整个冷加载过程无长任务或达到固定帧率。
最终仍需安装本轮候选包、重启 Zotero，用实际论文复核首次滚动。
